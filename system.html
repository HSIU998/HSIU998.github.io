本地 AI 系統

個人專案：長期記憶多代理系統。程式由 AI 撰寫；定方向、寫規格和驗收標準、拆任務、驗收與上線決定由我負責。

三個代表作我能負責什麼還沒做到的數字怎麼算附錄

這是什麼：個人專案，不是商品，我自己每天在用。要解決的問題是：AI 換了模型、開了新視窗、被廠商下架，記憶和身分就跟著消失。這套系統把記憶和身分放在本地，由程式保證每一輪都送得到，模型隨時可以換（業界叫 Agent Memory）。

三個代表作

問題是系統自己冒出來的，決定是我做的；程式由 AI 寫。每個案例都寫到「還沒做到的」為止。

案例 1 · 換模型

換模型，記憶和身分不跟著消失

問題
雲端模型三次被外部決定打斷：2026-08-31 改按用量計費、09-25 主力模型下架、10-04 額度用完全部停擺（約 6 天）。
我的決定
這不是成本題，是命脈題：狀態不放在模型裡，記憶和身分留在本地，模型可以換。
怎麼做
每個 agent 的記憶、狀態、身分設定都存在本機；雲端和本機模型走同一個介面，換模型不用改程式。
怎麼驗收
換之前先過「像不像本人」的基準尺，過不了就不換。
結果
換過 3 代模型，記憶和身分都延續下來；09-25 主力模型下架那天也沒有跟著消失。
還沒做到
10-22 試換過一次，兩小時內換回：A/B 量到語氣變的主因是多輪累積的上下文，不只是模型。說話那一層還在雲端。

案例 2 · 記憶召回

記憶明明在，卻想不起來

問題
一個 agent 說自己忘了一件很重要的事。查記憶庫，記憶一直都在，是模型沒照提示詞的指示去撈；寫在提示詞裡的事，模型可以選擇不照做。
我的決定
「查記憶」從拜託模型，改成程式在開口前先查好。之後四個地方出現同一型問題，定成規則：該由程式保證的事，不靠模型聽話。
怎麼做
程式判斷這一輪要不要查；用 jieba 斷詞、向量相似度加關鍵字命中找候選，語意、時間、情緒一起算分，去重、重排後放進這一輪。
怎麼驗收
上線那一輪 8 個 agent 各問 2 題，看有沒有執行、那筆記憶排第幾；之後用 47 題記憶考卷量「正確答案排得到眼前的比例」，過關線 50%。
結果
代撈 16／16 執行，那筆記憶從第 38 名排到第 1。
還沒做到
考卷 23%→43% 是開關打開時量的；正式環境為了日常對話品質先關著，正式設定 26%，還沒過 50%。

案例 3 · 驗收

燈全綠，不等於好了

問題
服務重開後燈全綠，用起來卻不對；第一批修復全部通過檢查，但那只證明「程式照寫的跑」，不證明用起來變好。
我的決定
先畫圖再施工；「確定好了」只算正式環境的紀錄證明過的，測試副本過、離線重放過的一律算觀察期。第二批 20 項看兩組測試（記憶考卷 47 題、日常聊天 103 句）決定照常上線，有問題的那一項預設關著。
怎麼做
整套系統畫成工程藍圖（214 個檔對照真實執行紀錄），問題分級登記成問題總表再分批修；每一項動手前先寫最終目標、量什麼、過關線。改動先在測試副本跑，守門程式擋住碰正式環境的動作。
怎麼驗收
每次上線前跑閉環檢查，紅燈 0 才上，每次留還原快照；上線後看正式環境的紀錄。
結果
修復帳本累計 267 項修復；代理核心 340 條問題裡 47 條確定好了、131 條在觀察期、41 條部分好了，不會全部算成「修好了」。正在影響運作的 120 條已動手 113 條（94%）。測試期間正式環境寫入 0 筆。
還沒做到
觀察期 131 條還在量效果；還沒碰的 117 條多數是潛伏問題和死碼。

Known limitations

還沒做到的

系統每天在用，也還在持續開發。這些是它目前還沒做好的地方，照實列出來；每一條都已經登記，有修復方案或下一步。

  • 記憶考卷還沒過關線。47 題考卷，答案排得到眼前的比例 23%→43%（開關打開時量的，正式環境為了日常對話品質先關著；正式設定 26%），過關線 50%。之後又上了幾批撈記憶的修改，還沒重量。
  • 世界模擬和日常系統還沒接上，而且模擬本身有 93 條問題要先修。模擬做出來的因果之書，目前沒有任何一條路接到日常運作的 agent；設計目標和實際狀態的差距見附錄 3。
  • 換模型之後，語氣可能會變。2026-10-22 試換過一次，兩小時內換回；A/B 量到主因是多輪累積的上下文，不只是模型，這一層還在修。換之前一定先過「像不像本人」的基準尺，過不了就不換。
  • 說話那一層還在雲端。完全搬回本機，要等新的模型伺服器到貨。

附錄 2 · Architecture

長期記憶多代理系統

內部代號「靈魂核心 SoulCore」與「世界樹 WorldTree」。兩層分開設計：代理核心保存每個 agent 自己的身分、記憶與狀態，可以搬到別的環境、換別的模型；共用層放跨 agent 的規則、因果紀錄、寫入閘門與服務間通訊。

共用層 · WorldTree
因果紀錄意圖→關係→情緒→事件→後果，記錄過程不只結果
寫入閘門動到核心資料的寫入只有 allow／deny／degrade 三種結果，可追溯、可回放、可稽核
服務間通訊HTTP 閘道、WebSocket、MCP 橋接、agent 之間的訊息
代理核心 × 9 · SoulCore
身分設定記憶庫（SQLite＋向量索引）知識圖譜情緒與狀態因果預測與驗證經驗蒸餾

每個代理核心是一個獨立的常駐行程，前面共用一個閘道；向量服務只有一份，9 個 agent 共用。

不是一個模型輪流扮演 9 個角色。9 個 agent 是 9 個獨立的常駐行程，各自有自己的記憶庫、狀態和身分設定，可以單獨停止、單獨重開，不影響其他 8 個。它們共用的只有說話的模型和向量服務；換模型時，每個 agent 的記憶跟身分都還在自己的核心裡。

·為什麼做這套系統記憶不能丟，也不能被廠商關掉›

這些 agent 是要長期使用的。記憶一旦丟了，就不是同一個 agent 了；所以記憶不能丟，也不能因為廠商下架、額度用完或漲價就被關掉。後面每一個工程決定都從這裡出發：要本地化、要把記憶保住、改核心之前一定先在沙盒試過。

每個角色有自己的記憶庫、個性和情緒狀態。每一輪對話都會先撈出相關的記憶，回覆之後再把這段對話寫回去，所以角色記得之前聊過什麼。會影響角色行為的修改，先評估影響、確認過才動：目前登記的 340 個問題裡，還沒改的 117 個中有 15 個標成「改之前要先評估對 agent 的影響」。

模型無關的狀態持久化

這兩年自己的系統換過 3 代模型（更早在聊天平台上用過 2 個）、跨過 3 個執行環境（雲端平台、第一台本機、現在的工作站），agent 的記憶與身分都延續下來。原則只有一個：狀態不放在模型裡。模型只負責把狀態轉成一句話；記憶、身分、情緒狀態存在核心，由程式保證每一輪都送得到。內部的說法是「換嘴不換人」。

附錄 7 · Methods

自己長出來的工法

這些做法不是從書上抄的，是做這套系統的過程裡一條一條定下來的。幾條業界本來就有名字（故意埋錯＝error seeding／mutation testing、一次只動一項＝控制變因），我是先撞到問題才用上，再照自己的情況調整。每一條寫做法，和它擋住的問題。

故障型錄

把出過的故障整理成類型，每一種都要答三件事：怎麼認出它、怎麼掃到它、怎麼修它。新的事故先查有沒有同型的；掃法寫得出程式的，就交給程式。

擋住的問題：同一型故障換個地方再出現，每次都當新問題從頭查。

原始需求標竿表

把 2024 年當初定規則時的原話，連同時間戳，當成量尺。拿現在的系統去比，差多少就是偏移，偏移就是待辦，原話就是驗收標準。

擋住的問題：做了兩年，忘了當初為什麼這樣設計；現在的問題幾乎每一個都對得回一條當初的設計。

三種標記，不准推測

每一個判斷都要標：程式碼和執行紀錄都看到、只在程式碼看到、推測待驗。沒看過的就寫「沒看過」。

擋住的問題：猜的跟確定的混在一起，後面的決定建在猜的上面。

互不引用的交叉驗證

重要的判斷走兩條彼此獨立的路：我讀程式碼，加上本機模型盲審（審查者先用埋好的錯考過）。兩邊不一致就交給人判。

擋住的問題：來源相近的兩個說法互相同意，被當成驗證。

沙盒守門

整套系統複製一份副本來測，守門程式保證測試期間正式環境寫入 0 筆。建沙盒時先放 13 隻金絲雀確認隔離有效，13 隻全部抓到才開始用。

擋住的問題：測試資料混進正式資料，之後分不清哪些是真的。

已知病清單

每日體檢只把「新的」和「變嚴重的」排在最上面。已知的登記在清單裡；修好就拿掉，再犯會自動浮回報告頂端。

擋住的問題：每天都紅的燈被看習慣，新的那一盞混在裡面沒人看見。

一次只動一項

比較兩個版本時，只改一個變因、同條件並排。量到的最大差異不一定是病因，要能單獨把那一項換回來、結果也跟著變，才算找到。

擋住的問題：一次改三樣，好了也不知道是哪一樣修好的。

換模型之前先考試

兩份考卷：一份看「像不像本人」，一份看「會不會抄別人的說話方式」。考過了、評估過影響，才換。

擋住的問題：換掉的是說話那一層，使用者感受到的卻是這個角色變了。

新舊並行換嘴

換說話的模型或推論引擎時，核心（記憶、身分、狀態）不動；新舊兩張嘴並行跑一段，用同一組尺比對（像不像本人的考卷、日常對話、長提示詞的首字延遲），過了才切。舊的嘴留著當退路。

擋住的問題：一次切過去，壞了沒有退路，而且分不清是嘴的問題還是核心的問題。

自報狀態不算量測

元件說自己「正常」「已校準」「已同步」，不當成量測結果，要另外量。開工第一步先核對基準（時間、版本、正式環境指到哪），不用推算的、不沿用上一次的。

擋住的問題：一個元件宣稱已校準的同一分鐘，量出來是錯的。

交接檔

工作分很多段、常換手。每次收工前寫交接檔：做到哪裡、還沒驗什麼、下一步是什麼；接手的先讀交接檔再動手。

擋住的問題：換手之後沒人知道上次做到哪，重做一遍。

成本跟著測試一起量

每次會呼叫雲端模型的整輪測試，跑前跑後各記一次帳戶餘額，換算成每一輪對話的實際成本。

擋住的問題：本地化值不值得，用感覺在吵。

我判斷問題的規矩

每一條都是我在大家說「沒問題」的時候找出問題之後定下來的，後來變成驗收時一定會問的題目。

燈綠了，還要問走的是哪一條路。從整套系統重開那次來：十二個服務埠全綠，我往下查，四個其實退回了慢速模式。紅燈會有人修，假綠燈沒人看，所以驗收不能只看燈。
「有在跑」要再問「有沒有做到」。從第一批修復那次來：全部通過檢查，我問每一項的最終目標達到了沒，當時答不出來。之後每一項都分兩層驗收：程式有照寫的跑，跟目標有沒有達到。
尺要量到真正在意的那一層。服務埠活著不代表服務正常，檔案存在不代表內容是對的。訂驗收標準時先問：這把尺量到的是外殼還是內容？
記憶的驗收要帶著歷史測。空白的測試資料測不出「失去歷史」，所以測試資料一定要帶種子歷史。
昨天好、今天壞，先找改了什麼。治標之前先比對變更，幾乎都能找到源頭。
下游好了，回頭確認上游。症狀消失不等於病根修好，驗收要回到源頭再量一次。
